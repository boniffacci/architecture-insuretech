# Анализ архитектуры InsureTech

## 1. Общий обзор текущей архитектуры
Система состоит из нескольких микросервисов:
- **core-app** (Kotlin, SpringBoot) — основной бизнес-сервис, хранит данные клиентов.
- **client-info** (Kotlin, SpringBoot) — сервис учёта клиентских данных.
- **ins-comp-settlement** (Kotlin, SpringBoot) — сервис расчёта страховых выплат.
- **payment-service** (внешний) — обработка платежей.
- Каждый сервис имеет отдельную базу данных PostgreSQL.

## 2. Проблемы и риски текущей архитектуры
1. **Синхронные вызовы между сервисами**
   - Увеличение нагрузки может привести к задержкам и сбоям.
   - Потенциальные блокировки при высокой частоте операций.

2. **Отсутствие Event-Driven подхода в ключевых сценариях**
   - Некоторые события (например, создание клиента) не публикуются в Kafka.
   - Сервисы напрямую обращаются друг к другу, что создаёт tight coupling.

3. **Нет атомарности при публикации событий**
   - События могут потеряться при сбое между записью в БД и отправкой в шину.
   - Без Outbox-паттерна возможна рассинхронизация данных.

4. **Невозможность горизонтального масштабирования некоторых сервисов**
   - Высокая нагрузка на базу данных одного сервиса блокирует операции других сервисов.

5. **Внешние сервисы (например, платежный)**
   - Ошибки или недоступность внешнего сервиса могут останавливать поток операций.

## 3. Предлагаемые улучшения
1. **Перевод ключевых взаимодействий на Event-Streaming**
   - События: `ClientCreated`, `PolicyCreated`, `SettlementCalculated` и др.
   - Сервисы-подписчики получают события из Kafka, исключая синхронные вызовы.

2. **Использование паттерна Transactional Outbox**
   - Каждый сервис, генерирующий события:
     - Создаёт запись в **Outbox Table** в рамках той же транзакции.
     - Специальный процесс отправляет события из Outbox в Kafka.
   - Это гарантирует атомарность и предотвращает потерю событий.

3. **Примеры потоков событий**
   - **client-info → Kafka**
     - `ClientCreated` → подписчики: `core-app`, `ins-comp-settlement`
   - **core-app → Kafka**
     - `PolicyCreated` → подписчики: `ins-comp-settlement`, `payment-service`
   - **ins-comp-settlement → Kafka**
     - `SettlementCalculated` → подписчики: `core-app`, `payment-service`

4. **Отдельные блоки Outbox на схеме**
   - Для каждого сервиса с Outbox добавить блок:
     ```
     [Service] --> [Service Outbox Table] --> [Kafka Topic]
     ```
   - Стрелка внутрь Outbox: локальная транзакция.
   - Стрелка из Outbox в Kafka: публикация события.

## 4. Риски после внедрения Event-Driven архитектуры
- Усложнение мониторинга и отладки потоков событий.
- Возможные дублированные события при сбоях (необходим idempotency).
- Требуется механизм повторной доставки и dead-letter queue для Kafka.

## 5. Заключение
Переход на Event-Driven взаимодействия с Transactional Outbox позволяет:
- Устойчиво масштабировать сервисы.
- Минимизировать потери событий при сбоях.
- Снизить tight coupling между сервисами и внешними зависимостями.
